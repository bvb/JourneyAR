## 1. Стек и ключевые решения

| Область | Решение | Запасной вариант |
|---|---|---|
| Сборка | Vite + TypeScript, монорепо на npm workspaces, без UI-фреймворка | — |
| 3D | three.js (версия зафиксирована) + GLTFLoader + Meshopt/KTX2. Формат **GLB** (бинарный glTF 2.0, один файл на сцену) | .gltf + .bin |
| Трекинг | **@webarkit/jsartoolkit-nft** напрямую, в Web Worker, все маркеры одновременно; ARnft — как образец реализации | **MindAR**: таргеты компилируются за секунды, обычно устойчивее на слабых текстурах |
| Аудио | Web Audio API, все файлы в MP3 (wav через ffmpeg с нормализацией) | Howler.js |
| Доставка | **Пока только локально:** HTTPS dev-сервер (`vite --host` + самоподписанный сертификат `@vitejs/plugin-basic-ssl`), чтобы проверять с телефона в локальной сети | mkcert, хостинг и PWA — позже |
| Тесты | Vitest (unit) + Playwright Test. Основной браузер — **Edge** (`channel: 'msedge'`) | **Изолированный Chromium**, который ставит Playwright (`npx playwright install chromium`): те же тесты, другой project |

Трекер прячется за интерфейсом `ImageTracker` (`start(source)`, `onFound/onLost/onPose`), и под него пишутся оба адаптера: NFT и MindAR. Какой оставить, решаем по замерам в виртуальной камере.

AR.js как основу не берём: это обёртка над более старым движком ARToolKit под A-Frame, она даёт меньше контроля над воркером и циклом кадров. WebXR image tracking не подходит: на iOS его нет.

### Источник кадров
В приложении есть интерфейс `FrameSource`: он отдаёт трекеру и фону видеопоток. Источник выбирается параметром URL `?source=`:

| `?source=` | Как работает | Для чего |
|---|---|---|
| `camera` (по умолчанию) | `getUserMedia` | обычная работа |
| `canvas` | ядро виртуальной камеры рендерится в том же окне в offscreen-canvas, поток берётся через `canvas.captureStream()` | автотесты Playwright: один realm, точный ground truth, управление через `window.__vcam` |
| `webrtc` | виртуальная камера в отдельной вкладке передаёт поток через `RTCPeerConnection` | ручная отладка: двигаем страницу в vcam и сразу видим результат в приложении |
| `video&src=…` | зацикленный видеофайл (webm/mp4) | регрессия на записях: из vcam (MediaRecorder) и снятых телефоном с настоящей книги |

- **Сигналинг WebRTC.** Если оба приложения на одном origin — через `BroadcastChannel`. Если на разных — через маленький WebSocket-ретранслятор, встроенный в dev-сервер. Второй вариант позволяет отдать поток vcam и на телефон в локальной сети, чтобы мерить трекинг на реальном железе. Какой вариант брать, решаем на пилоте.
- **Тестовые источники** включаются только в dev/test-сборке (через `import.meta.env`) и в боевую сборку не попадают.
- **Если ничего из этого не заработает:** флаги Chromium `--use-fake-device-for-media-stream --use-file-for-fake-video-capture=*.y4m`, затем OBS Virtual Camera.

1. **Источники кадров:** `camera` / `canvas` / `webrtc` / `video` по параметру URL (раздел 1). Базовые реализации и кнопка «Старт»/«Стоп» сделаны в фазе 3 (шаг 2); здесь остаются выбор камеры, зеркалирование PC-камер и `visibilitychange`.
   - Камера: по умолчанию задняя (`environment`), выбор устройства, зеркалирование для PC-камер.
   - Треки освобождаются по «Стоп» и при сворачивании вкладки (`visibilitychange`).
2. **Трекинг** — основа сделана в фазе 3 (шаг 3), см. там; осталось: калибровка угла обзора камеры телефона, поведение при сворачивании вкладки.
   Исходный план шага:
   - воркер получает уменьшенные кадры через transfer;
   - матрица проекции строится из `camera_para` под соотношение сторон видео;
   - поза сглаживается фильтром One Euro;
   - страница считается найденной после N кадров подряд;
   - **при потере сцена скрывается сразу.** Порог потери = 0 мс, но параметр остаётся в конфиге на случай мерцания;
   - активна одна сцена за раз.
3. **Сцены** ✅ (2026-11-06, `journey-ar/src/scenes/ar-scenes.ts`):
   - якорь страницы (поза трекера) → контейнер с `anchorMatrix(scene.anchor)` → GLB, подготовленный `prepareUnityScene`; рендер в gamma-режиме (`configureLegacyRendering`);
   - GLB загружается при первом обнаружении страницы; остальные — в фоне по порядку книги, после первого результата трекера (на телефоне трекер сначала получает процессор);
   - при каждом обнаружении анимации (`AnimationMixer`) и прокрутка UV (`PreparedScene.restart()`) начинаются с нуля; при потере сцена скрывается в том же обновлении;
   - дальность точечного света из Unity (в единицах таргета) умножается на ширину таргета в мм; щипок её не меняет, как в Unity;
   - контур страницы и оси — только с `?debug`;
   - вид и расположение всех пяти сцен на страницах совпадают с эталонами Unity (скриншоты через встроенную vcam);
   - e2e `scenes.spec.ts`: каждая сцена появляется на своей странице, исчезает в кадр потери, анимация при возвращении начинается заново, ошибок в консоли нет;
   - тесты WebRTC получают свою «комнату» ретранслятора (`?room=` у vcam и приложения), чтобы параллельные тесты не встречались; Playwright приложения — 3 потока (WebGL + WASM на страницу).

   Исходный план шага:
   - GLB грузится лениво при первом обнаружении, остальное подгружается в фоне после старта;
   - матрица привязки переводит координаты Unity (центр таргета, Y вверх, 200 единиц) в систему NFT (угол изображения, мм);
   - AnimationMixer, UV-скролл, свет;
   - **при каждом повторном обнаружении анимация начинается заново.**
3a. **Трекинг на телефоне — исправления после проверки пользователем** ✅ (2026-11-06). Пользователь проверил на Android с книгой: сцены стоят правильно, яркость устраивает; модели мелко подёргиваются при небольшом движении камеры (особенно летящий Creature), при повороте телефона трекинг перестаёт работать, щипок не работает (ещё не сделан — шаг 5), у Creature вместо света из головы чёрная пирамида, у Architecture будто нет освещения (шаг 3b).
   - **Сглаживание позы** (`src/tracking/pose-smoother.ts`): One Euro по каждому результату трекера — отдельно положение (мм) и поворот (кватернион); частота среза растёт со скоростью, оценённой по вектору скорости со знаком (дрожание в нём гасится, поэтому не ослабляет сглаживание). Затем на каждом кадре экрана поза плавно догоняет отфильтрованную (40 мс), чтобы модель не шла ступеньками между обновлениями трекера. Настройки по умолчанию — `minCutoff` 0.2 Гц (подобрано пользователем на телефоне: `?smooth=0.2`), `beta` 0.02 на мм/с, 1 на рад/с. При каждом обнаружении сглаживание начинается заново. `?smooth=off` выключает, `?smooth=<minCutoff>,<beta>,<rotationBeta>,<easing>` — подбор на телефоне. Unit-тесты: дрожание неподвижной камеры гасится больше чем втрое, отставание при 100 мм/с < 15 мм. В e2e показываемая поза в движении: та же точность, задержка ~220 мс против ~130 мс у сырой позы (Edge).

Теперь трекер всегда получает альбомный кадр: портретное видео рисуется в него повёрнутым на 90° по часовой, а проекция трекера поворачивает обратно (`rotated` в геометрии кадра). Угол обзора задаётся по длинной стороне (`?fov=`), трекер при повороте не пересоздаётся. После ошибки цикл трекинга не останавливается навсегда: трекер пересоздаётся через секунду.

При извлечении проекта из пересборки 2017 года материал потерял свой шейдер и получил встроенный Standard с тёмным цветом. Свойства материала в проекте сохранились.

4. **Звук** ✅ (2026-11-07), объёмный — по просьбе пользователя (решение 18). `src/audio/`.
   - **Оригинал:** в сборке 2012 года все музыкальные клипы двумерные (`m_3D: False`); `spatialBlend: 1` появился при конвертации в Unity 2017, а позиции AudioSource в сценах (1.2–2.5 ширины страницы сбоку) для 2D-клипов роли не играли. Поэтому пространственная модель своя.
   - **Пространство:** источник — над центром сцены на странице (центр привязки, +40 мм), слушатель — камера; позиция пересчитывается каждый кадр по сглаженной позе якоря (мм → м, система камеры) и меняется в `PannerNode` через `setTargetAtTime` (0.1 с). Модель `inverse`: полная громкость до 30 см, ~0.6 на 60 см, ~0.45 на 90 см (`rolloffFactor` 0.6); панорама `equalpower` — мягкий стерео-баланс по направлению.
   - **Трек:** при каждом обнаружении — с начала (нарастание 80 мс), при потере — затухание 80 мс и остановка (с шага 5a: страница, найденная снова в течение 3 с, продолжает трек с места остановки); громкость из `scenes.json` (из Unity, у всех 1.0). AudioContext создаётся кнопкой «Старт» (синхронно в обработчике клика — для iOS), на iOS 17+ `navigator.audioSession.type = 'playback'` (звук и при беззвучном режиме); при сворачивании вкладки контекст приостанавливается.
   - **Бесшовный повтор:** у этих MP3 нет LAME-заголовка с задержкой и хвостом кодировщика, поэтому границы петли находятся по декодированному звуку: тишина < 1e-4 в начале (23–56 мс) и в конце (29–640 мс), не больше 1 с с каждой стороны (`loopBounds`).
   - **Память:** MP3 скачиваются в фоне после «Старт», декодируются при первом обнаружении страницы; декодированными держатся два последних трека (иначе на телефоне до ~90 МБ).
   - **Тесты:** unit — границы петли и закон затухания; e2e (`audio.spec.ts`, два анализатора в графе: до и после пространственной обработки) — трек найденной страницы играет, при потере затихает, при возвращении начинается заново; при плавном удалении камеры с 30 до 90 см отношение уровней на каждом кадре совпадает с законом затухания для текущего расстояния (±0.12), трек не перезапускается.
   - **Найдено по ходу — «залипание» страницы.** Если страницу подменить одновременно с резким сдвигом камеры, трекер под нагрузкой иногда заново «находил» старую страницу на новой (ложное обнаружение: общая вёрстка — поля, значок, номер) и держал её с ошибкой трекинга ~1.6 (норма 0.1–0.9); поиск других страниц при этом выключен (`continuousDetection: false`), и исправить было некому. Теперь `PageSelector`: если ошибка активной страницы > 1.2 пять кадров подряд, трекер ищет другие страницы раз в 500 мс; найденная другая страница сменяет подозрительную; после 30 хороших кадров поиск выключается. e2e: восемь подмен страницы со скачком камеры — каждая распознаётся за 0.2–0.9 с (под нагрузкой). Playwright приложения — 2 потока.

   Исходный план шага:
   - AudioContext разблокируется нажатием «Старт» (без этого на iOS звука не будет);
   - при обнаружении трек играет с начала, при потере останавливается. Затухание 50–100 мс — только чтобы не было щелчка;
   - громкости берутся из Unity;
   - бесшовный loop через `loopStart/loopEnd`, иначе у MP3 слышна пауза из-за encoder padding.

- **Профилирование:** FPS, миллисекунды трекера на кадр, память, время до первой сцены. Средний телефон эмулировать троттлингом CPU через CDP.
- **Ручная проверка** через HTTPS в локальной сети на Android Chrome, iPhone Safari и PC с вебкамерой — на распечатках и на настоящей книге, по чек-листу.
- **Записи с книги.** Снять телефоном короткие видео с настоящей книгой и добавить их в `tests/recordings` как регрессию для `?source=video`.

## 4. Тестирование

**Браузеры.** Основной — Edge (`channel: 'msedge'`), запасной — изолированный Chromium из комплекта Playwright. Оба запускаются с временным профилем и не трогают пользовательские данные. Переключение — `--project=edge` или `--project=chromium`.

| Уровень | Инструмент | Что проверяем |
|---|---|---|
| Unit | Vitest | преобразования матриц, состояния found/lost, схема `scenes.json` (zod), AudioManager на моках, логика жеста масштаба |
| Ассеты | Node-скрипты | gltf-validator, бюджеты размеров, наличие анимаций, все ссылки манифеста существуют, NFT-файлы на месте |
| Трекинг | Playwright + `?source=canvas` | каждая страница: углы 0–60°, дистанции, поворот в плоскости, смена страниц, пустой кадр → потеря |
| Поведение | Playwright + `?source=canvas` | потеря → сцена скрыта в том же или следующем кадре; повторное обнаружение → анимация и звук с начала; масштаб сброшен |
| Регрессия на видео | Playwright + `?source=video` | записи из vcam и с настоящей книги: ожидаемая последовательность found/lost по таймкодам |
| WebRTC | Playwright, две вкладки в одном контексте | поток доходит, страница определяется |
| Визуальная регрессия | `toHaveScreenshot` | режим `?test`: анимация на паузе в момент t, фиксированная поза |
| E2E интерфейса | Playwright | старт/стоп, настройки, отказ в доступе к камере, нет камеры, разблокировка звука, щипок (CDP `Input.dispatchTouchEvent`) и колесо |
| Производительность | Playwright + CDP | FPS, мс трекера, время загрузки |

**Метрики по ground truth:** время до обнаружения, ошибка позиции (в % ширины страницы), ошибка угла, дрожание, число ложных срабатываний и пропусков. Это assertions с порогами, например: фронтально ≤ 1.5 с, ошибка ≤ 5 % ширины. На выходе — отчёт сравнения NFT и MindAR по каждой странице.

**Ограничения:**
- WebGL: локально браузер запускается с окном (на GPU), headless — на SwiftShader, это медленнее.
- Эмуляция мобильных в Playwright всё равно остаётся Chromium. iOS Safari проверяется только руками.

## 5. Как лучше использовать ИИ
- **Контекст.** CLAUDE.md с командами и правилами: ассеты собирать только скриптами из `tools/`, придерживаться схемы `scenes.json`, в `unity-data-project` менять только манифест, материалы и мусорные скрипты. Ключевые факты сохранены в памяти ИИ.
- **Ритм работы.** Каждая фаза начинается в plan mode, план утверждается, дальше реализация → тесты → коммит. Шаги маленькие, каждый можно проверить.
- **Долгие задачи в фоне.** Генерация NFT и экспорт из Unity запускаются фоновыми процессами с отслеживанием логов. Для batchmode-экспорта пользователь закрывает Unity.
- **Работа с изображениями.** ИИ видит картинки: так сопоставлены страницы со сценами и проверена обрезка page32 и page52. Так же будут сравниваться рендеры Unity и three.js и скриншоты тестов.
- **Замкнутый цикл.** Сценарий → запуск в Edge → метрики и скриншоты → исправление. Трекинг отлаживается без человека с телефоном.
- **Параллельность.** После фазы 0 ассеты, NFT и виртуальная камера независимы, их можно вести параллельными агентами в отдельных git worktree. Это быстрее, но дороже, поэтому только по явной просьбе.
- **Проверки.** Хук на typecheck/lint после правок, `/code-review` перед слиянием крупных частей.
- **За пользователем:** тесты на реальных устройствах с книгой, видеозаписи с книги, художественная приёмка, закрытие Unity перед batchmode-экспортом.

## 6. Риски
- **Unity 6:** ошибки компиляции и сломанные шейдеры после конвертации исправлены (фаза 1, шаг 1). Экспорт legacy-анимаций, lightmap и additive — главный технический риск фазы 1; на этот случай есть три запасных пути.
- **Слабые для NFT страницы:** page63 (мягкие градиенты). page166 опциональна. Выручат кроп или MindAR.
- **Привязка Creature и Landscape:** оригинальные таргеты были фрагментами страницы, смещение придётся подбирать.
- **Сигналинг WebRTC:** BroadcastChannel работает только в пределах одного origin. Запасной вариант — WS-ретранслятор.
- **iOS:** звук только после жеста пользователя, режим энергосбережения снижает FPS, браузерный зум мешает щипку.
- **Вебкамеры PC** часто с фиксированным фокусом, вблизи книга получается размытой.
